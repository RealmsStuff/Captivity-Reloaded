# Reference

Use the [example pack index](example-packs.md) to find a working starting point, the [schema index](schemas.md) for authoritative JSON contracts, and the generated [field-by-field API reference](api-fields.md) to browse every schema property. The [public asset-slot catalog](asset-slots.md) lists supported patch targets.

[Validation and errors](validation.md) explains the diagnostic system, while the searchable [validation/error-code catalog](error-codes.md) maps literal runtime codes to their source and message. [Troubleshooting](troubleshooting.md) covers common author failures, and the [Glossary](glossary.md) defines project terminology.

[Defaults and compatibility](defaults-and-compatibility.md) defines omission, fallback, migration, and save rules. [Resource limits](resource-limits.md) records safety ceilings. [Implementation status](status.md) separates working features from later work, while the [v1 release checklist](v1-release-checklist.md) tracks release readiness.

Before publishing one pack, use the smaller [mod-author test matrix](author-test-matrix.md). Project maintainers use the broader [release verification runbook](release-verification-runbook.md) for a complete game release.

The [Mod API changelog](api-changelog.md) records public-contract changes and [migration guides](migration-guides.md) provide author actions when versions diverge. The authoritative implementation draft remains `Docs/Modding/spec-v1.md`. Use [Implementation status](status.md) for current capability and the [Mod API v1 release checklist](v1-release-checklist.md) for unfinished verification and publication work.
